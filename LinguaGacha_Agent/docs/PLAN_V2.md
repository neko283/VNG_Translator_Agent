# LinguaGacha Agent 方案 V2：保留原工程，限定三种格式，支持持久化恢复

日期：2026-10-26。本文是实施前方案的本地副本；当前实现及验收结果见 [IMPLEMENTATION.md](IMPLEMENTATION.md)。

本方案依据用户最新要求，调整 原方案（历史文档）：首版只实现 TXT、KV-JSON、Message-JSON；保留原 `.lg`、`Item`、格式定位和写回规则；新增可跨会话读取的任务检查点、术语续用和恢复机制。原方案保留供查阅，涉及格式范围、工程存储和状态模型的冲突以本文为准。

上游分析基线为本地 `LinguaGacha` 仓库提交 `b7b18772d52d2af40acb73c905179c9703749e3e`。本文区分已经存在的上游行为与计划新增的能力；兼容性以该基线和经过验证的工程样本为准，不承诺兼容未知未来版本。

## 1. 目标和首版边界

用户在 Codex、Claude Code 等 coding agent 中加载技能，提供输入文件或已有 `.lg` 工程，由当前 agent 完成术语处理、翻译和审校，本地 CLI 完成解析、校验、保存、恢复和导出。用户不需要安装 LinguaGacha 桌面应用。

首版完整链路为：

```text
TXT / KV-JSON / Message-JSON，或已有 .lg
    → 按原规则导入、生成或读取 Item
    → 读取已有术语与保护规则，按需补充并保存
    → 分批翻译，校验后提交回 .lg
    → 检查与审校，修订再次提交
    → 按原格式、原定位和原写回规则导出
```

任一阶段中断后，可以从同一 `.lg` 读取工程事实和任务检查点继续。恢复不依赖原聊天记录仍在上下文中。

首版只包含以下格式：

|格式|原类型标识|范围|
|---|---|---|
|TXT|`TXT`|原逐行文本解析与写回，保留原可选双语输出能力|
|KV-JSON|`KVJSON`|原文作 key、已有译文作字符串 value 的对象|
|Message-JSON|`MESSAGEJSON`|含 `message` 字符串，以及可选 `name` / `names` 的数组|

其他格式只登记为未来扩展方向：首版不实现解析器、不注册适配器、不引入其专用依赖，也不以空实现声称支持。已有 `.lg` 中属于其他格式的数据必须原样保留；用户明确选择受支持的文件子集后才能执行相应任务。包含未支持格式的整工程翻译或导出请求应明确报告范围问题，不能静默漏掉文件。

首版不包含跨格式转换器。例如 TXT 翻译后按 TXT 输出，Message-JSON 按原 Message-JSON 写回；“任意输入统一转任意目标格式”不是本次目标。

## 2. 与原方案的主要调整

|事项|原方案方向|本版决定|
|---|---|---|
|工程主存储|新的工程目录和数据库，`.lg` 互操作后续考虑|直接使用原 `.lg`，不另建业务主数据库|
|条目模型|拆分 eligibility、translation_state、review_state 等|保留原 `Item` 字段及 `status` 语义|
|格式覆盖|逐步实现较广的首批及扩展格式|首版严格限定三种格式|
|格式定位|新核心需要设计统一契约|沿用原格式的 `file_path`、`row`、原文 key 和相关字段|
|恢复能力|围绕新状态模型构建|在原工程事实之上增加任务检查点和提交回执|
|术语保存|新工程规则存储|原 `rules` 和相关 `meta`；新任务只引用并记录使用版本|
|执行方式|预留多种执行器|先由当前 coding agent 完成翻译，CLI 提供确定性的本地操作|

本次不实施旧方案中的新业务状态模型。新增“任务阶段、批次、审校记录”属于调度信息，不能替代或重定义原 `Item.status`。

## 3. 复用原能力与必要改动

|模块|直接复用的内容|需要做的改动|
|---|---|---|
|工程数据库|`.lg` 表结构、原工程迁移、资产存储和压缩约定|拆出无桌面宿主的数据库装配；增加命名空间元数据读写|
|Item|原字段、枚举、状态解释、姓名与译文处理|CLI 提供查询与提交封装，不创建替代模型|
|三种格式|原读取器、写出器及必要辅助函数|独立注册三种格式，移除对完整格式服务的装配依赖|
|写入流程|`ProjectWriteStore`、指纹校验、修订校验、原条目更新规则|在同一事务中加入批次回执和检查点写入|
|规则处理|术语、文本保护、前后置替换、筛选和重复文本处理|提供无 UI 的读取、更新与规则快照接口|
|翻译与审校知识|适用于三种格式的工作流、提示规则和上下文组织方法|将应用专用工具调用改成 CLI 调用|
|宿主环境|不复用桌面聊天和窗口生命周期|新增共享技能说明及 Codex、Claude Code 的薄接入层|

“复用”指迁入或抽取对应源码和必要依赖，并以原测试和行为样本验证；不是在运行时要求用户保留整个原仓库。当前原 CLI 仍有 Electron 装配依赖，不能直接把它当作独立 CLI 发布。

数据库实现也包含原 Agent 聊天存储相关依赖。应拆分连接、工程迁移、工程读写与聊天服务装配，保留已有聊天数据及表，不为翻译流程启动原聊天系统。不能把“`.lg` 是 SQLite”理解为原数据库模块可以不经改造直接独立运行。

## 4. 三种格式必须保持的具体行为

### 4.1 TXT

- 按原文本解码和分行函数生成 `Item`，`row` 使用原行序号；不重新定义空行和末尾换行的解析规则。
- 写出时按原格式模块组合内容，使用 `\n` 连接文本。
- 已处理条目按原生成规则使用译文，其余条目回退原文。
- 双语输出使用原 TXT 的生成选项和逻辑，不推导为所有 JSON 格式也支持双语。

保留原行为并不等于保留输入文件的字节、换行编码或原始字符编码。首版不额外承诺这些保真能力。

### 4.2 KV-JSON

原格式示例：

```json
{
    "こんにちは": "",
    "ありがとう": "谢谢",
    "metadata": { "version": 1 }
}
```

- 顶层必须是对象；只把 value 为字符串的键值对解析为条目。
- `src` 是 key，`dst` 是 value。它不是把 `dialogue_001` 等任意标识作为 key、外语正文作为 value 的通用 JSON 翻译器。
- 空 key 对应 `RULE_SKIPPED`；非空且不等于 key 的已有译文对应 `PROCESSED`；其余沿用原未处理状态。
- 写回时读取 `.lg` 内保存的原始资产，定位原文 key，仅更新符合原规则的字符串字段；非字符串字段保留。
- 未处理条目回退原资产中的非空 value；若原 value 为空则回退 key。不能用工程当前的 `dst` 擅自替代该回退基线。
- JSON 序列化沿用原规则，包括四空格缩进。

### 4.3 Message-JSON

原格式示例：

```json
[
    { "name": "アリス", "message": "こんにちは" },
    { "names": ["アリス", "ボブ"], "message": "行こう" },
    { "message": "雨が降っている。" }
]
```

- 只提取数组中 `message` 为字符串的对象；`name` 或 `names` 按原优先级及过滤规则进入姓名字段。
- `row` 是提取后的条目序号，不应当作原数组中包含无效元素时的绝对下标。
- 写回按 `row` 排序，按原姓名选项生成 `name/message`、`names/message` 或仅 `message`。
- 原写出器会重建数组，不保留任意额外字段，也不恢复没有形成条目的数组元素。本版明确保留这一行为；原始文件仍保存在 `.lg` 资产中。
- 如未来需要保留额外字段，必须作为独立功能变更提出，不能混入本版并称为原行为兼容。

三种格式共同沿用 `read_translation_for_generation`：只有原语义中的 `PROCESSED` 使用 `dst`，其中空字符串也可能是有效译文；不能简单以“译文非空”判断完成。重复文本的生成回填仍走原生成层，不为方便恢复而批量改写原条目状态。

## 5. `.lg`、Item 和规则的保留方式

### 5.1 `.lg` 是唯一工程事实来源

保留原表和存储约定，包括 `meta`、`assets`、`items`、`rules` 以及已有其他表。原始资产继续使用原压缩存储方式。表中存在 PDF 或聊天相关内容，不表示独立 agent 已支持对应功能。

- 保留原工程迁移链；需迁移时先创建一致的工程备份，避免直接复制正在写入的 SQLite 文件造成不完整备份。
- 对未知或不能验证兼容的工程版本停止写入，报告原因。
- 不清空重建 `items`，不重新分配已有条目 ID，不删除未使用的资产、规则、表或未知元数据。
- 从原应用打开、修改、再由 agent 继续的兼容性需要专门验收，不能仅以 SQLite 能打开作为证明。

### 5.2 保留 Item

沿用原 `src`、`dst`、`name_src`、`name_dst`、`extra_field`、`tag`、`file_type`、`file_path`、`row`、`id`、`skip_internal_filter` 等字段。对外 DTO 的 `item_id`、`row_number` 命名沿用原公开契约，不修改内部模型。

保留原状态：`NONE`、`PROCESSED`、`ERROR`、`EXCLUDED`、`RULE_SKIPPED`、`LANGUAGE_SKIPPED`、`DUPLICATED`。

查询、筛选、重试、重复文本判断、人工更新和生成继续使用原语义。特别是：

- 恢复任务不能把跳过、排除或重复条目当作“漏翻”重新翻译。
- 模型调用失败优先记录为任务失败；若需要修改 `Item.status`，必须调用原来允许的状态更新路径。
- 原人工更新接口只接受其允许的状态；不能因为枚举包含 `ERROR` 就在人工补丁中任意提交它。
- 译文恰好与原文相同也可能是正确结果，提交时必须按原规则明确完成状态，不能只依赖字符串差异。

### 5.3 术语继续使用原规则存储

已确认术语写入原 `rules`，启用配置和相关修订信息沿用原 `meta`。保留原术语字段、稳定标识、顺序和匹配语义，不创建另一个有独立权威性的 `glossary.json`。

每次开始或恢复任务都重新读取工程中的规则及配置。给模型的术语 JSON、上下文文件属于快照，可以重建，不能反过来覆盖工程中较新的术语。

术语调查可以使用用户提供的参考文本或宿主可访问的官方资料。只有整理、确认并提交到工程的术语才成为后续批次依据；调查来源与未确认候选放在任务记录中。首版不额外开发网站抓取服务。

## 6. 新增持久化与恢复设计

### 6.1 存储位置

首版采用“原 `.lg` + 命名空间任务元数据 + 可再生工作目录”：

```text
project.lg                  # 原资产、Item、规则、任务检查点和提交回执
project.lg.agent-work/       # 可重建的快照、未提交候选、预览及详细报告
output/                     # 原格式生成结果
```

新增任务信息写入已有 `meta` 表的 `linguagacha_agent.*` 命名空间，使用带版本号的 JSON 值；不新增业务主数据库，不新增 Item 字段，不修改原表结构。建议按任务、批次、回执拆分键，避免每次写入一个不断增长的总 JSON。

这是本方案新增的扩展协议，不是原 LinguaGacha 已有功能。必须验证基线应用在打开、保存、迁移后保留未知命名空间元数据，并且原业务读取不受影响；未通过时不能宣称无损往返兼容。

工作目录不保存唯一的已提交事实。删除它后应能从 `.lg` 重建已完成任务的进度；尚未提交的模型草稿可以丢失并重新生成。工程迁移或移动后，工作目录可以重新创建，恢复不依赖旧绝对路径。

### 6.2 最小持久化信息

|记录|保存内容|作用|
|---|---|---|
|任务|任务 ID、协议版本、目标语言、选定文件与条目、运行选项、当前阶段|跨会话重建原任务范围|
|输入依据|资产身份与内容摘要、条目指纹、规则与配置摘要、相关修订号|判断之前的计划和结果是否仍适用|
|批次|批次 ID、条目范围、尝试 ID、准备/提交情况、失败原因|区分未执行、已提交和需要重新生成的批次|
|提交回执|尝试 ID、提交内容摘要、逐项接受/拒绝结果、提交后的修订|丢失回复后查询真实结果，避免重复提交|
|审校|条目 ID、被审校译文指纹、规则摘要、结论、待处理问题|精确恢复仍有效的审校进度|
|术语调查|已完成的调查范围、来源摘要、未确认候选、已提交规则标识|避免重复调查，并与正式术语区分|
|导出|范围、生成依据摘要、目标位置、完成文件及校验摘要|判断输出是否完整或需要重新生成|

任务阶段可以包含术语、翻译、检查、审校、导出，任务结果可以表示进行中、暂停、待处理和完成。这些是新任务协议的字段，绝不能写入原 `Item.status`。

原工程没有本方案检查点时，仍可根据原 Item 和规则建立新任务，接续已有译文和术语；但不能推断此前是否完成语义审校或资料调查。

### 6.3 原子提交与幂等重试

一次提交的顺序是：

1. CLI 生成批次及尝试 ID，读取最新条目、规则和修订，向 agent 提供快照。
2. Agent 产生原契约允许的补丁；本地进行结构检查，保留条目指纹，不允许模型修改格式定位字段。
3. 正式事务内再次检查指纹、相关修订和本批次的规则依据。
4. 原写入服务应用接受的条目或规则变更，同时保存逐项回执、更新任务检查点。
5. 事务提交后向宿主返回结果；外部快照和进度展示可以随后刷新。

第 4 步必须在同一个 SQLite 事务中完成。需要扩展原 `ProjectWriteStore` 的事务内写入准备能力，不能把检查点放在事务结束后的 `onCommitted` 回调中，否则仍可能出现译文已保存、进度未保存的问题。

保留原部分接受语义：无效或陈旧条目被拒绝，其他合法条目按原规则提交；事务失败则回滚本次接受部分。检查点记录逐项结果，不能把整个批次笼统标成成功。

同一尝试 ID 与相同内容再次提交时，返回已有回执；同一 ID 携带不同内容时拒绝。部分失败条目需要重新读取、生成新的尝试，不能复用旧尝试 ID 修改内容。

检查点及回执的写入是新增能力；原条目的接受、拒绝和状态更新规则保持不变。规则过期的批次不得按旧依据继续提交，应重新准备。仅写入任务元数据也不能伪装成原译文已发生变更。

### 6.4 恢复算法

执行 `resume` 时：

1. 打开 `.lg`，完成兼容性检查，读取真实 Item、规则、配置和任务记录。
2. 根据任务 ID 恢复范围；多个未完成任务且无法确定目标时才要求用户选择。
3. 核对任务快照与当前工程。条目、规则或配置变化时，使受影响的旧批次或审校结论失效，生成新的工作依据。
4. 查询已提交回执，排除已经成功提交的尝试；恢复期间不重复执行已确认写入。
5. 根据原条目状态与有效审校记录计算剩余工作，返回下一批及对应上下文、当前术语和保护规则。
6. 每次正式提交继续保存检查点；完成后按原格式生成并核验输出。

默认继续尚未完成的工作。针对原 `ERROR` 条目提供明确的重试入口；重译 `PROCESSED` 条目必须属于用户选择的重译或审校修订范围。不得因“恢复”自动覆盖全部已完成译文。

术语发生变化时保留已经提交的译文事实，将受影响内容列为待检查；是否重译由任务策略或用户指令决定，不把已完成条目直接重置为未翻译。

### 6.5 中断与变化处理

|场景|恢复行为|
|---|---|
|模型生成中断，尚未提交|原工程不变；重新生成未完成候选|
|事务执行中进程退出|由 SQLite 保证回滚或提交；重开后以工程和回执判断|
|提交成功但宿主没收到回复|读取原子保存的回执，不重复写入|
|批次部分接受|保留成功结果，对拒绝项重新读取和生成|
|工作目录被删除|从 `.lg` 重建进度和规则快照，未提交草稿重新生成|
|原应用修改了译文或术语|重新读取事实，使过期批次、审校记录失效|
|外部输入文件被修改|继续使用 `.lg` 中已导入资产；不在恢复时偷偷重新导入|
|导出中断|核对输出记录与实际文件，从当前工程重新生成缺失或不一致输出|

首版对自身的写命令串行化，并保留原事务内并发校验。原应用不一定遵守新 CLI 的进程锁，因此锁不能替代指纹和修订校验。源资产在工程内发生变化时暂停受影响范围并要求重新规划，不尝试自动合并新的行号映射。

恢复保证是“已提交事实不丢失、可确定剩余工作”，不是恢复模型进程、隐藏推理或任意未提交的聊天草稿。

## 7. 独立运行结构和拟议接口

```text
coding agent
    → 共享翻译技能：编排、术语判断、翻译、语义审校
    → lg-agent CLI
        → 原工程领域逻辑与写入服务
        → 三种原格式适配器
        → 原规则和质量检查能力
        → 新任务检查点、回执与恢复服务
    → 原 .lg 与导出文件
```

默认使用当前 coding agent 的模型能力，不强制另外配置模型 API。不在首版实现递归启动 agent、多执行器、常驻服务或 MCP 服务。

以下命令是待实现的接口示意，当前尚不能运行：

```sh
lg-agent doctor
lg-agent import ./input --project ./project.lg
lg-agent inspect ./project.lg
lg-agent start ./project.lg --target-language zh-CN --workflow full
lg-agent resume ./project.lg --task <task-id>
lg-agent next ./project.lg --task <task-id>
lg-agent apply ./project.lg --task <task-id> --attempt <attempt-id> --changes ./changes
lg-agent export ./project.lg --task <task-id> --output ./output
```

`resume` 和 `next` 返回结构化的剩余任务及批次输入，由宿主继续执行模型工作；CLI 本身不凭空产生译文。`apply` 的尝试 ID 属于外围提交协议，原 `updates.jsonl` 的条目补丁字段及校验规则继续沿用。

技能负责按照用户范围调用以上操作：全流程包含审校；用户仅要求翻译或导出时不强制扩展任务。格式检查始终执行，失败候选应先修复再提交。全流程完成需要指定范围内的翻译、检查、审校和导出均达到任务要求。

导出仍使用原生成和回退规则。用户可以导出尚未全部翻译的工程，但报告必须列明回退和未完成情况；“成功导出文件”不等于“全流程任务完成”。

### 本地依赖

- 采用 TypeScript 开发，发布可直接运行的 Node.js CLI；目标 Node.js 基线沿用原方案，在实现阶段锁定并验证具体版本。
- 必需运行能力包括原 SQLite 驱动路径和 zstd 资产解压缩，以及三种格式和规则模块实际使用的依赖。
- `doctor` 必须检测实际 SQLite、zstd 和工程读写能力，不能只检查版本号。仅有 `sqlite3` 命令并不足以运行核心。
- 无需 Electron、桌面 UI、浏览器渲染器、PDF 引擎，也不安装其他格式专用依赖。
- 只保留 `.lg` 文件本身无需运行时；读取、继续翻译和导出时才需要上述 CLI 与运行环境。

当前开发环境的 Node.js 18 不具备计划采用的原生 SQLite、zstd 接口，不能直接认定为目标运行环境；后续实现时处理运行时安装与校验，本次只更新方案。

|阶段|交付内容|通过条件|
|---|---|---|
|P0：兼容性验证|锁定源码基线，梳理依赖，验证 `.lg` 样本与命名空间元数据往返|无 Electron 打开工程；原应用保留新增元数据且原业务不受影响|
|P1：原核心抽取|工程迁移、数据库、Item、规则、提交服务的独立装配|旧工程读取和原更新语义通过测试，ID 和未涉及的数据不丢失|
|P2：三种格式|仅注册 TXT、KVJSON、MESSAGEJSON，实现导入与原格式导出|和原实现的同输入输出对照通过，包括原有回退行为|
|P3：持久化恢复|任务元数据、规则依据、事务回执、审校检查点、恢复命令|崩溃与回复丢失场景可恢复，已提交内容不重复写入|

后续其他格式另行排期，不作为本版未完成的实现任务，也不在上述阶段顺带加入。

## 9. 验收标准

### 格式和工程兼容

- TXT 验证空文件、空行、末尾换行、混合换行、未处理回退与原双语规则。
- KV-JSON 验证空 key、已有译文、value 等于 key、非字符串字段和原资产回退，确认非通用 ID 键值翻译。
- Message-JSON 验证姓名优先级、多人姓名、无效数组项、提取后的排序、额外字段不保留及原姓名写回选项。
- 验证已处理空译文、同文译文、跳过和排除状态、重复文本，以及原补丁部分接受语义。
- `.lg` 在基线原应用与 CLI 间往返后，原条目 ID、资产、术语、其他格式内容和新增任务记录符合预期。
- 新任务记录不影响原业务修订语义；旧工程缺少新记录时可以接续，但不得虚构历史审校结果。

### 恢复和术语

- 在候选生成、事务提交前后、宿主回复丢失及导出期间注入中断，核对恢复结果。
- 用同一尝试 ID 重试，不能重复修改工程；不同内容复用同一尝试 ID 必须拒绝。
- 混合成功与拒绝的批次，只对尚需处理的条目创建新尝试。
- 删除可再生工作目录、更换宿主会话或移动工程后，可从 `.lg` 恢复已提交进度。
- 术语在暂停前提交，恢复后的模型输入必须使用新术语；旧候选不得越过规则依据校验。
- 审校后修改译文或规则，相关审校记录失效；未受影响且依据仍有效的记录继续使用。
- 完成状态与实际工程一致，不能以聊天中的“已完成”或单一进度百分比代替核验。

### 独立运行

- 在未安装 LinguaGacha 桌面应用、未保留原仓库的环境中执行三种格式的全流程。
- 构建和运行不隐式下载或启动 Electron，也不加载未支持格式的专用模块。
- 分别在 Codex 和 Claude Code 中验证当前会话翻译、关闭会话、重新打开同一工程继续的流程。

## 10. 取舍与后续扩展

本版优先保持原工程和格式行为，减少新的数据模型与转换层。代价是仍需理解、抽取原核心及其迁移依赖；原格式的限制也会被保留，例如 Message-JSON 不保留任意额外字段。

恢复层提供跨会话能力，但增加了事务内记账、规则依据检查、协议版本和兼容性测试工作。采用已有 `meta` 扩展可避免增加表结构，但回执需要后续制定保留与压缩策略；首版不自动清理仍有恢复价值的记录。

未来若增加其他格式，应继续以原适配器和原工程模型为基础，逐个验证依赖、定位、回填和恢复行为，再加入能力清单。格式扩展无需先替换 `.lg` 或 `Item`；跨格式转换、无损 Message-JSON 扩展、额外模型执行器可单独设计。
