# LinguaGacha_Agent 跨引擎翻译工作流

适用于已完成文本提取与最小运行验证的游戏。先阅读 [通用实施流程](通用实施流程.md)，把下述工作区绑定到 `<user_work_root>/release/<game_id>/work/`。各游戏无需复制本文件，只记录具体参数、任务 ID、偏差与结果。

## 1. 可行性与职责

**现有 Agent 负责提取后的文本翻译、术语管理、审校、恢复与导出；无需修改它的代码或技能。** 各引擎的资源读取、脚本解析、文本转换、字体与补丁封装由对应引擎工具和游戏适配层完成。

这里的 Agent 是“宿主模型 + 本地技能 + CLI 工程管理”的组合。CLI 不调用模型 API，也没有一个单独执行完就自动译完整部游戏的 `translate-all` 命令；必须由宿主持续读取任务、理解上下文、生成译文并提交，直到完成审校。中断后可换会话继续。

当前本地实现与各引擎接入的关系如下：

| 能力 | 代码核对结果 | 使用方式 |
| --- | --- | --- |
| 输入格式 | TXT、KV-JSON、Message-JSON | 主输入采用仅含可翻译字段的 Message-JSON |
| 术语提取 | 宿主读取网页/全量语料，CLI 保存 terms 与 glossary；没有独立抓站命令 | 翻译前执行 [术语提取流程](术语提取流程.md) |
| 完整流程 | `terms → translation → review → export → completed`，另有阻塞处理 | 使用 `--workflow full` |
| 工程与恢复 | `.lg` 内保存资产、译文、规则、批次、回执和审校记录 | 同一版本文本继续使用同一工程 |
| 翻译提交 | `translations` 经过译后恢复与结构检查；支持部分接受 | 每批检查回执，只重做未接受部分 |
| 上下文 | `next` 附带同文件行号前后两条 | 宿主另读场景简介、人物关系及必要原文 |
| 重复文本 | 按同文件、相同正文、可见姓名槽位协调重复项 | 所有出现位置都要复核，不能只看代表项 |
| 自动检查 | 含保护段、行数及质量警告 | 补充引擎脚本语法、编码和回填位置检查 |
| 导出 | 可导出尚未完成的任务，可能回退原文 | 正式回填前必须通过额外完整性检查 |

需要已安装并激活 Node.js >=24.22.1；每个实施环境先执行 `doctor`。运行结果记录在游戏实施目录，不能由某台机器的成功结果推断其他环境已可用。

依据为本地 [共享翻译技能](../LinguaGacha_Agent/skills/linguagacha/SKILL.md)、[CLI 协议](../LinguaGacha_Agent/docs/CLI.md)、[任务调度源码](../LinguaGacha_Agent/src/engine.ts)、[格式入口](../LinguaGacha_Agent/src/formats.ts) 和 [实现与验证边界](../LinguaGacha_Agent/docs/IMPLEMENTATION.md)。以下步骤采用当前实现支持的命令，待开发部分会单独标明。

## 2. 第一步：生成翻译输入与独立定位清单

建立有效资源目录后，由对应引擎转换工具生成两部分输出；工具尚不存在时先实现并通过小样验证：

1. `translation/input/`：只放要导入 Agent 的 Message-JSON，每条必须具有字符串 `message`；可选 `name` 或 `names` 仅用于显示姓名。
2. `translation/mapping/`：保存原资产哈希、原路径字节、原文范围／语法节点、提取器定位字段、原编码、换行、稳定 ID、正文和姓名的回填策略、控制标记映射。不要放进 Agent 输入目录，防止被当成翻译素材。

输入示例仅表示格式，不是某个游戏的实际台词：

```json
[
  {"name": "登場人物A", "message": "また会えたね。"},
  {"message": "扉を開ける"}
]
```

对应定位采用 `(输入相对路径, 从 0 开始的数组序号)` 连接稳定 ID，再由稳定 ID 连接原脚本位置。导入后，通过 `query` 的 `file_path/row_number` 核对并记录工程 `item_id`。其中 `item_id` 只在本工程中有效，`fp` 则必须每次从新批次取值，不能把旧指纹当成永久 ID。

关键约束：

- Message-JSON 仅接收合法消息对象，不能混入无 `message` 的元数据条目，否则导入时跳过条目会改变行号对应关系。
- 不把 `id/path/context` 等字段放入 Message-JSON 并依赖其导出保留；当前写出器只重建 `name/names/message`。
- 不采用 `{"稳定ID":"日文"}` 形式的 KV-JSON；当前 KV 格式把 key 当原文、value 当已有译文，会错误翻译 ID。
- 不直接导入含指令的完整引擎脚本；通用 TXT 读取器不会理解其脚本结构，且输出统一换行为 `\n`。
- 剧情按场景组织，保留路线与原文件顺序；可用带序号的 ASCII 输入文件名，使导入排序稳定。独立清单保留原日文资源路径。
- 默认仅将对白、旁白整理为消息输入。选项框文本保持原文；设置、菜单、图片文字及其他非对白/旁白文案不进入翻译输入。姓名只在对白上下文需要时作为可选字段提供，是否翻译显示姓名由游戏方案明确。章节标题不自动纳入范围。记录排除位置，回填时核对未修改。

非显示命令尽量留在原脚本模板中；嵌在一句话内且必须保留的标记，可转换为无歧义占位符，如 `__TR_CTL_0001__`，在独立清单保存原标记，确认正文中不存在占位符碰撞。注音需明确区分底文、读音及标签，不默认开启 `--clean-ruby` 丢弃内容。

转换层必须先通过“提取后不翻译，再恢复原脚本”的往返检查：正文与原位置一致，控制结构无变化，原字节可以保留的区域逐字节一致。是否已有转换层及其验证情况，以对应引擎和游戏目录的记录为准。

## 3. 第二步：准备上下文并处理重复句

在 `translation/context/` 保存人物关系、称呼、角色语气、路线与场景顺序、场景摘要，以及分支条件。它们由宿主显式阅读，不会因文件存在就自动进入 `next` 的模型输入。摘要只记录文本支持的信息，未确认的称谓和关系标为待核实。

当前 `next` 只提供同文件前后两条，`query` 可读取任务范围的全部条目。因此：

- 翻译前先读取场景背景；代词、省略主语、称呼转变等问题需要向前后扩展阅读。
- 对选择分支分别提供上下文，不把存储顺序相邻的不同分支误当成连续对话。
- 完成一个场景后更新简短摘要和待解决问题，供后续批次与新会话恢复使用。
- 术语阶段先用 `query` 或已提取的完整语料整理角色与术语；反复调用 `next` 不会自动翻页遍历全部术语素材。

导入前按同文件、原文、可见姓名检查重复组。诸如“そう”“……”“いい”等短句需逐处判断能否共享译文。当前 CLI 没有关闭去重的命令（增强为可选，不是实施前置条件）：应在冻结输入前，按真实场景拆分；仍需不同译文的重复出现位置，可以分配到独立输入文件，并通过上下文清单保留关联。不要向原文添加假词或伪造姓名来规避去重。

允许共享的重复项仍必须检查所有出现位置，因为 Agent 的 `full` 审校阶段只逐项要求 `PROCESSED` 条目的审校，`DUPLICATED` 条目不会自动各自获得独立语义审校。若后期发现共享不合适，重新整理受影响输入并建立新版本工程，按稳定 ID 和原文哈希迁移已确认译文，重新审校；不要直接修改 SQLite 身份字段。

## 4. 第三步：先做 Agent 小样，再冻结全量输入

默认取游戏开头到第一个选项出现前的对白、旁白作为预翻译范围；选项框内容保留原文。单独建立小样工程，完整走完 `full`、导出、恢复脚本与游戏内验证。人工确认字体、格式和原文选项显示正常后，再开始全量翻译与补丁制作；必要时另补长句、换行、占位符和重复句的合成检查。

小样验收包括：条目和定位一致、姓名可正确分离、占位符可恢复、译后处理仅执行一次、审校修改生效、重复项输出正确、导出文本能回填并显示。发现问题先修正转换层，再冻结全量 `input` 与 `mapping` 的版本和哈希。

之后导入整个工作集，建议同一游戏版本使用一个工程以共享术语和恢复记录；当前实现每次操作读取工程快照，尚未优化大工程分页，应先测量批次响应时间，确有瓶颈再按路线拆分并制定术语同步规则。

下面及后续命令均以仓库中的 `LinguaGacha_Agent` 为工作目录；先激活 Node。将 `LG_WORK` 设置为该游戏实施目录下 `work` 的绝对路径，后续命令始终引用同一个工作区。示例占位路径必须替换：

```sh
LG_WORK='/用户指定的绝对路径/release/game-a/work'
node bin/lg-agent.mjs doctor
node bin/lg-agent.mjs import "$LG_WORK/translation/input" --project "$LG_WORK/translation/jobs/translation.lg" --source-language ALL --target-language ZH
node bin/lg-agent.mjs inspect "$LG_WORK/translation/jobs/translation.lg"
node bin/lg-agent.mjs start "$LG_WORK/translation/jobs/translation.lg" --workflow full
```

此处示例使用 `ALL → ZH`，实际源语言在每个游戏方案中确认。对于日文游戏，但短对白或旁白可能只有汉字、拉丁字母或数字，应在导入后逐项审计过滤状态，避免仅因日语检测没有假名而漏掉。若选择 `JA`，也必须先验证语言跳过清单。模型的翻译任务说明仍须明确实际源语言和简体中文目标。

记录 `start` 返回的实际任务 `id`；后文的 `TASK_ID` 和 `ATTEMPT_ID` 都是待替换占位符。默认使用覆盖全体输入的一个任务；若用 `--files` 分批建任务，需额外维护任务范围总表，证明所有文件都有归属。

## 5. 第四步：术语提取、来源核对、入库与保护规则

先执行独立的 [术语提取步骤](术语提取流程.md)：读取游戏指定网站，结合全部有效语料抽取候选，记录页面出处、原文稳定 ID、读音/别名、语境限制、译名决定和修订版本。官方原文与游戏语境优先，数据库辅助交叉核对；未知读音、冲突或不可访问页面显式记录。调查资料放在同一工作区的 `terms/`，不要导入为剧情文本。

```sh
node bin/lg-agent.mjs query "$LG_WORK/translation/jobs/translation.lg" --task TASK_ID
node bin/lg-agent.mjs next "$LG_WORK/translation/jobs/translation.lg" --task TASK_ID --limit 20
```

在 `terms` 阶段，根据全量素材和背景整理姓名、称呼、地名、家族关系、专用词、反复出现的表达及文体要求。正式术语通过 `quality.glossary.creates/updates` 写入工程；待核实内容记入 `terms.candidates`。独立 Markdown 术语表只作阅读资料，不能代替工程里的生效规则。

对于上述自定义占位符，可建立 `text_preserve` 正则 `__TR_CTL_[0-9]+__`，并启用 `custom` 模式。该正则只保护转换层实际生成的占位符，不要使用可能吞掉正常对白的宽泛表达式。创建规则时遵守当前协议的字段与 `sort` 要求，修改现有规则使用当前 `id/fp`。

规则提交与译文提交分开；启用规则的命令示例：

```sh
node bin/lg-agent.mjs configure "$LG_WORK/translation/jobs/translation.lg" --kind glossary --enabled true
node bin/lg-agent.mjs configure "$LG_WORK/translation/jobs/translation.lg" --kind text_preserve --mode custom
```

调查进行中用 `terms.done: false` 和 `sources/notes/candidates` 保存进度。全量候选覆盖完成、关键冲突解决、确认术语入库并启用、回执及版本核查通过后，才可结束术语阶段。所有配置变更后重新 `next` 获取有效批次，再提交 `terms.done: true`。仅记录候选不会使其生效。前后替换默认不批量增加，确有必要时逐条验证，避免误改台词和标记。

## 6. 第五步：逐批翻译、提交并检查回执

1. 调用 `next --limit 20`，读取返回的 `phase`、`attempt`、当前规则和条目；长段落或复杂分支改为 5～10 条，不能仅按数量估算上下文长度。
2. 宿主依据 `request.text_src`、可选 `request.actor_src` 翻译，同时查看原文、邻近上下文及场景资料。保留语气、信息量、控制符和必要换行，不擅自简写或补写剧情。
3. 将结果写成 UTF-8 的提交文件。示例中的 ID 与指纹必须用本批实际值替换：

```json
{
  "translations": [
    {
      "item_id": 123,
      "fp": "从本次 next 原样复制",
      "text_dst": "我们又见面了。",
      "actor_dst": "角色甲"
    }
  ]
}
```

`actor_dst` 仅在条目有姓名请求时提交。没有姓名请求则省略；多姓名字段的可见槽位限制需按实际输出处理，其余姓名不能假定已全部翻译。`request: null` 时按技能协议提交原文供译后恢复，不凭空制造译文。

```sh
node bin/lg-agent.mjs apply "$LG_WORK/translation/jobs/translation.lg" --task TASK_ID --attempt ATTEMPT_ID --changes "$LG_WORK/translation/changes/batch-0001.json"
```

4. 检查回执 `status`、`item_results`、拒绝原因和 `checkpoint_saved`。部分接受时保留已保存结果，重新 `next` 后修复剩余条目；不要用同一个 attempt 提交修改后的内容。
5. 每个场景完成后检查漏译、角色称呼和上下文连续性，更新背景记录。重复调用 `next → 宿主翻译 → apply`，按返回阶段继续，不能自行跳过 `blocked`。

`translations` 会执行译后恢复；已恢复的最终文本不能再次送入此入口。终稿修订使用下一步的 `items` 入口。

## 7. 第六步：逐条审校与全局复核

`next` 返回 `review` 后，对每条原文和译文检查主语、否定、时态、指代、关系、称呼、角色语气、术语及控制符。自动质量警告需要判断和处理，不能当成已经完成的语义审校。

修订与结论可以在同一批提交：

```json
{
  "items": [
    {"item_id": 123, "fp": "本次审校批次指纹", "dst": "修订后的最终译文"}
  ],
  "reviews": [
    {"item_id": 123, "fp": "同一本次指纹", "verdict": "pass", "note": "结合前文确认说话对象，并统一了称呼。"}
  ]
}
```

没有修订时只提交 `reviews`；不能确认时提交 `needs_revision` 并记录具体问题。不得未经逐条阅读就批量填写 `pass`。姓名修订使用协议允许的 `name_dst`，不要改原始角色标识。

完成局部审校后，还需逐场景通读，并针对以下项目做全局复核：同一角色跨路线的称呼、伏笔与后文解释、同义术语、重复句的每个出现位置，以及正文显示长度；另核对选项原文和分支行为未改变。

若修改术语或保护规则，先保存规则再重新 `next`；旧批次失效，相关审校结论也会失效，需要按当前依据重新确认。终稿修改应回到 `.lg` 内保存并重新导出，避免工程与外部译文产生两套权威版本。

## 8. 第七步：中断恢复与定向返修

```sh
node bin/lg-agent.mjs inspect "$LG_WORK/translation/jobs/translation.lg"
node bin/lg-agent.mjs resume "$LG_WORK/translation/jobs/translation.lg" --task TASK_ID
node bin/lg-agent.mjs next "$LG_WORK/translation/jobs/translation.lg" --task TASK_ID --limit 20
```

工程是恢复依据，不重新 `import` 覆盖已完成进度。新会话先读共享技能、工程阶段及场景资料，再继续模型工作。

- `apply` 的响应丢失：先 `receipt --attempt ATTEMPT_ID` 查询；不存在回执时可原样重放同一请求。
- 需暂停：使用 `pause --task TASK_ID --reason ...` 保存原因。
- `ERROR` 条目：明确失败文件范围后用 `start --files ... --retry-errors --workflow full` 建立返修任务，并在任务总表记录其与原任务的关系。
- 已完成文本确需重译：使用限定文件范围的 `--retranslate`，先备份工程；该选项会重译所选文件中已完成条目，不能误当成只重译某一个 ID。
- 外部原文变化：不会自动进入 `.lg`。重新提取并校验映射，建立新版本输入／工程；按原文哈希迁移仍有效的结果，变化部分重新翻译审校。

除 `.lg` 外，原资源、定位清单和上下文资料也要保留；`.lg` 可以恢复翻译流程，但不会替代引擎 回填所需的外部映射。

## 9. 第八步：正式导出、完整性检查与回填

```sh
node bin/lg-agent.mjs resume "$LG_WORK/translation/jobs/translation.lg" --task TASK_ID
node bin/lg-agent.mjs export "$LG_WORK/translation/jobs/translation.lg" --task TASK_ID --output "$LG_WORK/translation/output"
```

导出到独立目录，不能覆盖输入、定位清单或工程。正式验收不能只看文件生成成功，应同时满足：

| 检查 | 放行条件 |
| --- | --- |
| 任务状态 | 导出返回 `completed`，恢复检查仍为完成；翻译与审校剩余量均为 0 |
| 范围覆盖 | 所有范围内剧情文本都进入任务或有明确的保留原文决定；图片文字和非剧情界面文案按范围排除，不计漏译 |
| 过滤与重复 | `EXCLUDED/RULE_SKIPPED/LANGUAGE_SKIPPED/DUPLICATED` 全部有核对记录；重复项逐处通过语境检查 |
| 回退清单 | 审计 `fallback_items`；它也会列出可由代表项回填的重复项，需检查实际输出，不能一概判失败或一概忽略 |
| 零条目资产 | 审计 `zero_item_assets`，确认没有漏提取本次范围内的剧情文本 |
| 定位对应 | 每个输入文件与输出文件的消息数量、顺序及姓名结构一致，逐项能映射回稳定 ID |
| 文本完整性 | 范围内剧情的空译文、与原文相同的译文及日文残留均经过人工判断；控制标记数量和顺序符合约定 |

转换层随后执行：

1. 按“输入文件 + 数组序号 → 稳定 ID”读取译文，核验原资产和映射哈希未变化。
2. 恢复自定义占位符，处理显示姓名而不改内部角色键，并执行目标脚本的字符串转义。
3. 若使用 VNTextPatch，基于保留的原提取结果更新它要求的译文字段，再交给 VNTextPatch 回填；不把 Agent Message-JSON 直接传入其回填接口。
4. 若使用游戏适配解析器，按已验证的原文范围／语法节点替换；对每种脚本或文本格式使用正确的引号和转义规则。
5. 将终稿转换为该游戏小样已验证的正文编码，保持包内路径编码独立；进行脚本结构及资源引用检查。
6. 按对应引擎流程，完成字体排版、增量打包和游戏内验证。发现翻译问题时回到 `.lg` 修订后重新生成，不只在最终补丁里手改。

## 10. 待实现内容、目录和完成标准

Agent 的基础流程已有实现。引擎侧应提供以下三类适配能力，名称为接口约定，不代表每个引擎均已实现：

| 拟开发模块 | 输入 → 输出 | 核心验证 |
| --- | --- | --- |
| `prepare_translation` | 有效脚本／提取器结果 → Message-JSON、定位与上下文清单 | 提取完整、顺序稳定、同句不误合并、原文哈希可追踪 |
| `check_translation` | `.lg` 查询／导出报告、译文、定位清单 → 检查报告 | 覆盖率、过滤／回退、占位符、重复句、条目对应 |
| `restore_translation` | 审校后译文、原提取结果／原脚本 → 待封包资源 | 原文不变时往返正确、只改目标区域、编码及转义正确 |

每个引擎在工具说明中明确这些接口的实现状态。先用其现有接口完成小样；只有遇到无法通过转换层解决的限制，再考虑增加按条目返修或可配置去重等功能。

```text
<游戏实施目录>/work/translation/
  input/          # 冻结的 Message-JSON，Agent 仅导入此目录
  mapping/        # 稳定 ID、原脚本位置、编码、控制标记、原提取结果
  context/        # 场景背景、角色语气、分支关系、恢复说明
  jobs/           # translation.lg 与版本备份
  changes/        # 提交草稿；有效进度以 .lg 中回执为准
  output/         # Agent 导出的已审校 Message-JSON
  reports/        # 覆盖率、遗漏、回退、重复句和术语复核记录
```

正式批次使用 `work/runs/<批次>/`，本文件的 `LG_WORK` 指向该批次根目录。新建正式全量 `.lg`，不依赖开场测试工程或旧导出；恢复同一正式批次仍使用原工程。遵守 [独立构建与安装契约](正式构建与安装流程.md)。

执行顺序为：**转换与小样 → 冻结全量输入 → 导入正式工程 → 网页及语料术语提取 → 核对与入库/保护规则 → 分批初译 → 逐条审校 → 全局复核 → 导出审计 → 恢复脚本 → 游戏内验收 → 返修与独立正式构建 → 原版首次安装/还原验收。** “翻译完成”要求范围内剧情完整、审校通过且可可靠回填；“汉化补丁完成”还须满足字体、安装和实机验收。图片文字及菜单等非剧情界面文案保持原样。
