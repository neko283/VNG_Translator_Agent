# 跨引擎游戏汉化实施流程

本流程适用于后续接入的各引擎。各阶段的顺序和记录格式共用，具体资源格式、解包器、脚本语法和补丁机制由对应引擎工具处理。识别引擎后，agent 必须先读取 `Game_Engine_Tools/<引擎>/README.md` 及其链接的使用和适配说明，再执行解包、回填、封包等操作；可从 [引擎工具入口](../Game_Engine_Tools/README.md) 查找。

所有游戏数据、专属适配器和结果记录均位于工具目录之外的用户指定工作目录。默认只翻译对白和旁白，选项框原文必须保留。

## 阶段与记录

| 阶段 | 工作 | 产物与通过条件 |
| --- | --- | --- |
| 0 建档 | 从空白模板创建 `<user_work_root>/release/<game_id>/`；确认版本、平台、翻译范围 | 方案、日志、结果状态初稿；未完成项明确标注 |
| 1 识别与基线 | 检查程序、资源格式、官方更新；记录文件哈希和工具版本；测试原版运行 | `work/manifest/`；把原版故障与补丁故障分开 |
| 2 分别解包 | 每个资源包提取到独立目录；保留路径字节和内容哈希 | `work/unpacked/`；原文件不变，结果可追踪 |
| 3 建有效资源 | 比对同路径更新，验证实际加载优先级 | `work/effective/` 与来源清单；未知优先级不可标已确认 |
| 4 小样闭环 | 无改动往返、少量中文、字体、长句、分支、存读档 | 开头到首个选项前的小样运行记录；人工确认字体、格式后才批量翻译 |
| 5 全量提取 | 分离显示文字与指令，生成 Message-JSON、稳定 ID 和定位清单 | `work/translation/input/` 与 `mapping/`；原文往返检查通过 |
| 6 术语提取与入库 | 读取指定网站和全量语料，提取候选、核对来源/称呼、解决关键冲突，写入正式 `.lg` | `terms/` 来源、候选、决定和版本；glossary 启用、回执通过后完成 terms；见 [术语流程](术语提取流程.md) |
| 7 翻译审校 | 基于正式术语逐批初译、逐条审校、全局复核、断点恢复 | `.lg` 工程、回执与覆盖率报告；见公共 Agent 工作流 |
| 8 回填构建 | 从本轮原资源回填，重新构建全字符集字体并封包 | `patch_files/`、`build/`；不以旧测试补丁为输入 |
| 9 原版首次安装 | 在仅游戏本体目录中预检、首次备份、安装、重复安装和还原 | 无旧补丁/旧 backup 也能完成；见 [正式构建与安装](正式构建与安装流程.md) |
| 10 实机验收 | 分支、结局、显示、安装卸载、存档兼容 | `qa/` 与结果报告；已测和未测范围分开 |

术语步骤须覆盖冻结的全量原文和约定参考来源，不能仅查看首批 `next` 条目。当前由宿主阅读抽取、CLI 保存 terms/glossary，不假定有独立抓站命令。正式批次建议使用 `work/runs/<批次>/` 作为工作区。

## 数据与适配契约

- 输入资源保持只读，输出进入独立工作目录。目录名、包内路径编码、脚本正文编码分开处理。
- 定位清单保存原文件哈希、原包路径字节、原文范围／语法节点、稳定 ID、输入文件与数组序号、姓名和控制符规则。
- Game-specific ID、文件路径、跳转标签、条件、语音和角色资源键不交给模型修改。图片姓名与文本姓名分别识别。
- Message-JSON 只保存 `message` 和可选 `name/names`；稳定 ID 和回填信息另存，避免导出丢失。
- 全部命令、工具来源和版本写入日志。任何模型输出都需经过结构检查和语义审校，不能把 CLI 无报错视作翻译合格。
- 大文件可按需提取；不要因为只做剧情翻译就把音频、图片全部解包或重新分发。

引擎层按需提供 `prepare_translation`、`check_translation`、`restore_translation` 三类适配能力。这是接口约定，不表示当前所有引擎已有这些工具。游戏特殊语法通过单独适配实现，复用验证过的公共能力。

## 完整性与发布

正式制作从新工作区和原版游戏重新生成清单、资源、术语、翻译、字体及发布包；已冻结的正式翻译产物可用于复建。测试算法可以复用，旧测试 payload、派生字体、`.lg`、manifest 和 backup 不作为必需依赖。隔离重建及无旧补丁的原版首次安装必须单独验收。

翻译覆盖率的分母是本次明确纳入的剧情文本。选项框文本、设置、菜单、图片文字和其他非对白/旁白文案按范围排除；范围内的过滤、重复、回退、空译文、原文残留需要逐项核对。自动重复合并不能替代每个出现位置的语境判断。

保持原本可用的游戏基线，先测试最小覆盖方式，再决定独立补丁包、散文件或分包重建。记录基线哈希、补丁清单、构建版本、安装与卸载方法、必要组件和字体许可。新旧存档兼容、所有路线和结局是否已测都应明确列出。

修改译文应回到 `.lg` 工程后重新导出和构建。原文或规则改变时重新检查映射与审校有效性，不能靠只修改成品补丁维持进度。

## 实施记录约定

每次实施在游戏目录下追加一条日志，内容包括日期／批次、目标、输入版本、命令及工作目录、工具版本、输出路径、通过／失败／未验证结果、下一步。失败记录保留原因及恢复办法，不覆盖成“成功”。

结果报告至少区分：工具自测、资源提取、文本转换、中文小样、全量翻译、语义审校、回填构建、游戏运行、发布验收。仅完成调研时，结论写“可开展实施”，不能写“汉化完成”。

重复实施使用相同游戏目录；保留阶段性构建和日志，版本基线不同则分开记录。`.lg` 是翻译进度依据，日志是实施依据，二者与映射文件均须保存。
